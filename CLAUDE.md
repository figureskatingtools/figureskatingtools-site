# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

The **single host for figureskatingtools.com** — an auth-gated App Service that serves the home page **and all tool frontends path-based** on one domain (`/`, `/judgepapers/`, `/scoremodifier/`, `/protocolgenerator/`, `/tools/banner/`, `/tools/gdpr/`), proxies each tool's API to its separately-deployed Function App, and owns the **platform competition registry** (create/select a competition once, every tool operates on it). Tool *backends* stay in their own repos (`fs-judgepapers`, `fs-scoremodifier`, `fs-protocolgenerator`, and the private `fs-gdpr-tool` behind the Tools menu's GDPR Removal Tool); their `frontend/` dirs are legacy and live here now.

## Workspace layout

npm workspaces monorepo (root `package.json`, workspaces: `packages/*` and `site`):

- **`packages/shared-ui`** — `@figureskatingtools/shared-ui` v3 (internal): path-based site nav (`DEFAULT_TOOLS` in `src/nav.ts`), plus the **competition state module** (`src/competition.ts`: `getActiveCompetition`/`setActiveCompetition`/`subscribeActiveCompetition`, localStorage key `fst:active-competition:v1` — stores `deletionDate`, `access` and `owner` too, so an extend reaches other tabs via the `storage` event; API client for `/api/competitions` incl. `extendCompetition(id)`; pure `retentionInfo(deletionDate, startDate, now)` → `{day, daysLeft, dueSoon, beforeEvent}`) and the nav **competition selector** (`src/competition-selector.ts`, renders into `#fst-nav-competition`; degrades to nothing if the API is unavailable) plus the shared competition dialog it opens (`openCreateCompetitionDialog` / `openEditCompetitionDialog` — one form in two modes: create POSTs everything, edit PATCHes only the changed fields). v3 is consumed via workspace symlink only; the external GitHub Packages publish (v2.x) exists solely for the tool repos' legacy frontends and dies with them.
- **`site`** — one Vite project, **seven HTML entries** (`index.html`, `judgepapers/`, `scoremodifier/`, `protocolgenerator/`, `tools/banner/`, `tools/gdpr/`, `admin/` — see Admin panel). Small tools live in the nav's **Tools** dropdown (`SMALL_TOOLS` in shared-ui `nav.ts`); one with a backend of its own gets an entry in the router's `SMALL_TOOL_APIS` (`/tools/gdpr/api/*` → `FUNCTION_APP_URL_GDPRTOOL`). Each app is its own document with its own unscoped `style.css` (`site/src/<app>/`) — CSS never crosses documents; don't import one app's CSS from another. Shared chrome is `site/src/shell.ts` (`fetchUser()` → `GET /userinfo` flat shape incl. `name` from the principal's name claim and `isAdmin`, `loginUrl(appPath)`/`logoutUrl()`, `renderSignInView`, `setupUserMenu`). Per-app API base constants: `const API_BASE = '/<tool>/api'` — never root-absolute `/api/...` inside tool apps (bare `/api` is the platform registry).
- **`server`** — the zero-dependency Node router (`server.js`): static hosting of the Vite dist with per-prefix SPA fallback, `GET /userinfo`, `GET /health`, the public `GET /judgepapers/download?t=<token>` (the e-mailed or copied judges'-papers link → judgepapers `/api/download_judge_papers`, which 302s to a short-lived blob URL; the second Easy Auth `excludedPaths` entry, so keep `JUDGEPAPERS_DOWNLOAD_PATH` and `webapp.bicep` in sync), and streaming proxies `/<tool>/api/*` → `FUNCTION_APP_URL_<TOOL>` and `/api/*` → `FUNCTION_APP_URL_PLATFORM`, injecting `x-proxy-secret` (per-target `PROXY_SHARED_SECRET_*`) + the `x-forwarded-user-*` identity headers (see Auth). Per-prefix CSP (protocolgenerator gets pdf.js allowances). Bodies are piped, never buffered (25 MB PDF / 100 MiB ZIP uploads flow through). `redirect-server.js` is the cutover-era 301 helper for old subdomains. See `server/README.md` for the env contract.
- **`infra`** — subscription-scoped Bicep: per-env site RG (`rg-fs-site-<env>`) with the Web App (B1, Easy Auth v2 via MI federated credential), platform storage (`stfsplat*`: `competition-data` + `app-package` containers, `competitions`, `retentionclock`, `adminlog`, `users`, `useridentities` and `competitionaccess` tables), platform Function App (`func-fs-platform-*`, FC1 Python 3.13), the HOVTP listener's **own** storage account (`stfshovtp*`: host state + its `app-package`), RBAC (`platform-roleassignment.bicep` account-scoped for the platform app; `hovtp-host-roleassignment.bicep` account-scoped on the listener's own account; `hovtp-data-access.bicep` granting the listener *only* the `competition-data` container + the `competitions` table on platform storage; `shared-data-access.bicep` granting tool Function Apps (`TOOL_PRINCIPAL_ID_*`) Blob Data Reader on the `competition-data` container and Table Data Reader on the `retentionclock`, `useridentities` and `competitionaccess` tables (never `competitions`, which holds e-mails and sender IPs, nor `users`) — child-resource scoped like the HOVTP module; the older account-scoped grant must be removed by hand, `infra/MIGRATION.md` §2d), DNS in the shared persistent `rg-fs-dns` zone (apex = plain **A record to the Web App's `inboundIpAddress`** + `asuid` TXT; `test` = CNAME + `asuid.test` TXT; domain-wide Mailgun e-mail records declared by both envs: apex SPF TXT `v=spf1 include:mailgun.org -all`, `mta._domainkey` DKIM TXT, `_dmarc` `p=reject` with reports to Mailgun, `email` tracking CNAME — Mailgun sends judgepapers' `no-reply@` mail and is the domain's only sender), custom-domain binding + managed cert + SNI. **`infra/functions/`** is the platform competition API. **`infra/MIGRATION.md`** documents the one-time manual steps (GitHub env vars/secrets, Entra grants, cutover order, teardown).
- **`infra/hovtp`** — the **HOVTP listener**, a *separate* Function App (`func-fs-hovtp-*`, FC1 Python 3.13, own `asp-fs-hovtp` plan and its **own storage account** `stfshovtp*` for Functions host state + deployment package, shares `ai-fs-platform`) so the platform's only anonymous internet-facing surface can be stopped or revoked on its own. FS Manager pushes ODF/PDF messages to `POST|OPTIONS /api/v1/hovtp` (no credentials exist in the protocol; that single versioned route is what goes in FSM's Endpoint field). Parsing is **body-first** — the competition code comes from `OdfBody/@CompetitionCode`, falling back to an `X-*-Competition*` header; the URL never carries a code, and HOVTP headers are optional. Only `DT_PDF`, `DT_PARTIC`, `DT_PARTIC_TEAMS`, `DT_SCHEDULE`, `DT_SCHEDULE_UPDATE` are stored (`HOVTP_ALLOWED_DOCUMENT_TYPES` overrides); anything else is logged and dropped with a 200. Participant files (`DT_PARTIC`, `DT_PARTIC_TEAMS`, their `_UPDATE`s) lose their `BirthDate` attributes/elements before storage (`strip_birth_dates`: byte-preserving, re-parsed and compared, else 451 and nothing stored); the platform's file-upload route does the same to an uploaded ODF participant file (422 `birth_dates_not_removed`), the code byte-identical in both apps (`tests/test_parity.py`). Trust is per **(competition, source IP)**: table rows `PK=HOVTPSOURCE`, sessions/serial numbers in `PK=HOVTPSESSION`. An unaccepted IP's files are quarantined in `competition-data/<guid>/fsm-pending/<ip>/` (invisible in the file pool) and moved flat into `<guid>/fsm/` when an operator accepts the source. `HOVTP_ENABLED=false` is the kill switch (Bicep-owned, so it survives redeploys; GitHub var `HOVTP_ENABLED`). **Both environments are published through a Front Door Premium + WAF -> APIM layer** (`https://test-api.figureskatingtools.com/api/v1/hovtp`, `https://api.figureskatingtools.com/api/v1/hovtp`; Terraform in the separate `azure-publishing` repo): that makes `X-Forwarded-For` four entries long with FSM first, so `HOVTP_TRUSTED_PROXY_HOPS=3` in both (`hovtpTrustedProxyHops` in the bicepparams), and because hop counting is spoofable while the raw `*.azurewebsites.net` hostname stays reachable, APIM injects `X-Proxy-Secret` — compared constant-time against `PROXY_SHARED_SECRET` (GitHub secret `PROXY_SHARED_SECRET_HOVTP`), `403` on a mismatch for POST/OPTIONS, fails open when unset, `/api/health` never gated. Storage is **isolated**: account-scoped roles only on its own `stfshovtp*` account (the Functions host creates `azure-webjobs-*` itself, which container-scoped RBAC cannot), and on the platform account nothing but container-scoped `competition-data` + table-scoped `competitions` — so it cannot reach the platform app's `app-package` deployment zip. `COMPETITION_DATA_ACCOUNT` names the platform account, because `AzureWebJobsStorage__accountName` no longer does (`_data_account_name()`, kept byte-identical with the platform app by `tests/test_parity.py`). Own pytest suite — see Common commands.

The backends fail closed: give router and backend the same secret (`PROXY_SHARED_SECRET_<TARGET>` / `PROXY_SHARED_SECRET`), and the local platform `ALLOWED_TENANT_IDS=00000000-0000-0000-0000-000000000001` (the `DEV_FAKE_USER` tenant). (The tool repos switch to fail-closed in their own `feature/competition-access` branches.)

## Auth

**App Service Easy Auth v2 (AAD)** gates the whole origin platform-side (`requireAuthentication`, `RedirectToLoginPage`; excluded: `/health`, `/judgepapers/download`, the public landing page — `/`, `/index.html`, `/signin`, `/landing/*`, `/assets/*`, `/favicon.png`, `/apple-touch-icon.png`, `/robots.txt`, `/llms.txt` — the privacy notice `/privacy`, `/privacy/*`, the terms of use `/terms`, `/terms/*`, the retired Finnish notice `/tietosuoja`, `/tietosuoja/*` (router 301 → `/privacy/`, `RETIRED_PRIVACY_PREFIX`), the self-hosted fonts `/fonts/*`, and the External ID "no access yet" page `/no-access`, `/no-access/*`). Signed-out visitors at `/` get the static `site/public/landing/` page (plain HTML/CSS). Easy Auth injects **no** principal headers on excluded paths, so at `/` the router recognises a signed-in browser by its `AppServiceAuthSession*` cookie (or a principal header, or `DEV_FAKE_USER`) and serves the home page; that page's `/userinfo` and all APIs stay gated, so a stale or forged cookie only reaches the home page's sign-in view. `/assets/*` (Vite bundles — open-source code, no data) is public so that page always loads. Keep `LANDING_DOCUMENT_PATHS`/`SIGNIN_PATH` in `server.js` and `authExcludedPaths` in `webapp.bicep` in sync. The privacy notice (English only: `site/public/privacy/index.html` + `privacy.css`, on `/landing/landing.css`) needs no router logic: `serveStatic` serves it to everyone. It is linked from the landing and home footers, `renderSignInView` and the `setupUserMenu` dropdown; it states the retention rules, so update it (and its "Last updated" date) whenever what is stored or for how long changes. The terms of use (`site/public/terms/`, English only, same styling, cross-linked, linked next to it everywhere) hold the GDPR Art. 28 terms users accept at the External ID sign-up (controller Markus, users process on his behalf, as the notice says); they reference the notice for retention and hosting, so keep the two consistent. Fonts are **self-hosted** (`site/public/fonts/`: `fonts.css` + versioned woff2 from `@fontsource-variable/*` + OFL licences); every document links `/fonts/fonts.css`, the CSP allows no third-party font or style host, and `/fonts/*.woff2` is cached immutable, so a font update needs new file names. Every sign-in link goes through the router's `GET /signin?return=<path>` (same-origin paths only) → `/.auth/login/$AUTH_LOGIN_PROVIDER` (default `aad`), so the planned move to Entra External ID is a setting, not a frontend change. No client secret: a user-assigned MI federated credential (`OVERRIDE_USE_MI_FIC_ASSERTION_CLIENTID`), FIC + redirect URIs maintained by the deploy workflow via Graph. Frontends read identity from `GET /userinfo` (router decodes `X-MS-CLIENT-PRINCIPAL`); `loginUrl()` builds `/signin?return=…`, which the router turns into `post_login_redirect_url` (App Service syntax — not SWA's `_uri`). Locally there is no `/.auth/*`; use `DEV_FAKE_USER`.

**Identity = Entra tid + oid, never the e-mail.** The router (`requestIdentity` in `server.js`) takes `oid` (`…/claims/objectidentifier` or `oid`) and `tid` (`…/claims/tenantid` or `tid`) from the decoded principal; without both (GUIDs) `/userinfo` is `{authenticated:false}` and `/api/*`, `/<tool>/api/*`, `/tools/gdpr/api/*` are `401 unauthorized`. `ALLOWED_TENANT_IDS` (comma list; `webapp.bicep` defaults it to the deployment tenant, GitHub var `ALLOWED_TENANT_IDS` overrides; empty = nobody) → `403 tenant_not_allowed` for anyone else. It forwards to **every** backend (platform, tools, GDPR tool; not `/judgepapers/download`) `x-forwarded-user-tid`, `-oid`, `-email` (lowercased, display/audit only; printable ASCII checked **before** lowercasing — U+212A KELVIN SIGN lowercases to `k` — else no e-mail at all, never forwarded; same rule in the platform's `_normalize_email`), `-name` (`encodeURIComponent`), `-admin: 1` (admins only — the `Site.Admin` app role, see Admin panel) and `-terms-accepted: 1` (only when the principal carries the External ID sign-up's `termsAccepted` claim as `true`; the platform records it, the tools ignore it); the outbound allow-list drops any client copy. `DEV_FAKE_USER` gets tenant `00000000-0000-0000-0000-000000000001` and an e-mail-derived oid (`devObjectId`). Every backend **fails closed**: `PROXY_SHARED_SECRET` must be set and match (`hmac.compare_digest`), identity only from those headers (no `X-MS-*`, principal-JSON or Bearer fallback).

**Entra External ID (phase B; runbook `infra/EXTERNAL-ID.md`).** One Easy Auth provider (`azureActiveDirectory`, `/.auth/login/aad`), two tenants, picked by GitHub var **`AUTH_TENANT_MODE`**: `workforce` (default; workforce app + MI FIC, as above) or `external` — client `AUTH_EXTERNAL_CLIENT_ID`, issuer `https://<AUTH_EXTERNAL_AUTHORITY_HOST, default <tid>.ciamlogin.com>/<EXTERNAL_TENANT_ID>/v2.0`, `loginParameters` `scope=openid profile email`, and **no credential** (no `clientSecretSettingName`/secret/cert/FIC, ever: Easy Auth then runs the ID-token `form_post` flow; the site needs no access/refresh tokens). The workflow refuses `external` without both ids. No custom OIDC provider: Easy Auth's custom OIDC always uses the code flow, which needs a secret. test runs `external`, prod `workforce` until phase C go-live (one var; switching back is the rollback); `/signin` and `AUTH_LOGIN_PROVIDER=aad` are the same in both. The External ID apps' redirect URI is `https://<host>/.auth/login/aad/callback`. `main.bicep` appends `EXTERNAL_TENANT_ID` to the effective `ALLOWED_TENANT_IDS` in **both** modes (old sessions survive a switch) and writes it to the router and the platform as `EXTERNAL_TENANT_IDS`. Router: an identity whose **tid** is in `EXTERNAL_TENANT_IDS` takes its e-mail **only** from the `email` claim (or its `…/claims/emailaddress` form) — never `userDetails`/`preferred_username`/the name — under the same ASCII/lowercase rules, and must carry the app role `EXTERNAL_ACCESS_ROLE` (default `Site.Access`; `roles` claim or `…/claims/role`; no admin exception) — else documents 302 to the public **`/no-access/`** page (`site/public/no-access/`: privacy-notice styling, English only, `no-access.js` reads `/userinfo`; `shell.ts` `fetchUser()` also redirects there), `/userinfo` is 403 `access_not_granted` with only `name` + `email`, and every API and `/admin/*` is 403 `access_not_granted`, never proxied (this replaces Entra's "Assignment required"; keep `NO_ACCESS_PATH`/`PUBLIC_PATH_PREFIXES` in sync with `authExcludedPaths`); workforce tids are unchanged. Platform: a new identity of an `EXTERNAL_TENANT_IDS` tenant (no `useridentities` row) gets **503 `migration_pending`** before any write — no user is created until the phase C linking code exists (`IDENTITY_PROVIDER_ENTRA_EXTERNAL = "entra-external"` is reserved for it); existing rows and workforce identities are unchanged. Diagnostics show `authTenantMode` + `externalTenantCount` (router) / `externalTenantCount` (platform).

**Router request hygiene** (`server.js`, before any routing): a path with a dot segment (`.`/`..`, also `%2e`), an encoded separator (`%2F`/`%5C`, also double-encoded), a backslash, NUL or a bad escape is **400** (`isUnsafePath`); every route then matches the canonical path (`canonicalPath`: decoded, `//` collapsed) and the proxy/static server get that path re-encoded per segment (`encodePath`), never the raw one. **CSRF:** every non-`GET`/`HEAD` request to `/api/*`, `/<tool>/api/*`, `/tools/gdpr/api/*` needs `Sec-Fetch-Site: same-origin`, or a matching `Origin` only when `Sec-Fetch-Site` is absent (`isSameOriginRequest`) → else **403 `cross_site`**, before the identity gate, never proxied. Tool backends' `delete_competition` is POST-only and owner-only (403 `platform_owner_required`, a non-"gone" `PlatformErrorCode` in shared-ui); no site frontend calls it.

## Competition registry (platform API)

`infra/functions/function_app.py`. Every route normalises `{id}` once (`_route_competition_id`: strict lowercase GUID via `fullmatch`, so no trailing newline; anything else **404 `not_found`**) and uses only that for every entity/blob/HOVTP/access lookup; `_GUID_RE` is always `fullmatch`ed. Every user route goes through `_require_user` (fail-closed secret, forwarded tid/oid, tid in its own `ALLOWED_TENANT_IDS`) → `User(user_id, email, name, is_admin)` and then `_require_access` (see Access model). Table `competitions`, two row kinds: PK `COMPETITION`/RK GUID (the entity) and PK `CODE`/RK normalized-code → GUID (uniqueness + O(1) lookup; created first on insert, 409 `code_in_use` on conflict, freed on soft delete). Routes: `GET|POST /api/competitions`, `GET|PUT|PATCH|DELETE /api/competitions/{id}`, `POST /api/competitions/{id}/extend`, `GET /api/competitions/{id}/access`, `PUT|DELETE /api/competitions/{id}/access/{userId}`, `GET /api/users/search?q=`, `GET /api/users/recent`, `GET /api/users/me`, `GET /api/health`. Create accepts `date` or `startDate`. Python `normalize_code` must stay identical to TS `normalizeCompetitionCode` in shared-ui (NFD diacritic folding — there's a test). FSM ingest is live: the HOVTP listener (`infra/hovtp`) writes into `competition-data/<guid>/fsm/` (accepted) or `<guid>/fsm-pending/<ip>/` (quarantined), and this API owns the operator side of it — `GET /api/competitions/{id}/hovtp/sources`, `POST /api/competitions/{id}/hovtp/sources/{ip}/accept` (`{"days":1|2|3|7}`, also extends; moves the quarantined files into `fsm/`), `POST …/{ip}/reject` and `DELETE …/{ip}` (revoke; already-attached files stay). The home panel's **Edit** dialog drives `PATCH /api/competitions/{id}` through shared-ui `updateCompetition` (partial body, only the changed fields); because a code rename moves the `CODE` row, the dialog warns that FSM pushes still using the old code get a 451 from the HOVTP listener until FSM is reconfigured.

**Retention — one clock, owned by the platform.** One retention rule per competition: the tools keep no clock and no extend route of their own. The `COMPETITION` row owns `DeletionDate` (`"YYYY-MM-DDT00:00:00Z"`, midnight UTC of creation day + `RETENTION_DAYS=60`), exposed as `deletionDate` and ignored on PUT/PATCH. `POST …/extend` sets `max(current, today midnight) + EXTENSION_DAYS=7` (etag-conditional with retries, no cap, 404 when deleted/unknown; stores `ExtendedCount`/`LastExtendedUtc`, never who). `DELETE` is soft but pulls `DeletionDate` to the next midnight (never later) and writes `DeleteReason="user"` with **no** `DeletedBy` e-mail; the CODE row is freed at once (`_release_code_row` — only if its `CompetitionId` still matches). Rows older than the column read as `max(created+60 d, LEGACY_DELETION_FLOOR)` (a fixed constant in `function_app.py`, so no extension already granted in a tool is cut short). The timer `retention_sweep` (03:00 UTC, the tools' schedule too) → `_run_retention_sweep(now, purge_enabled)`: backfills missing `DeletionDate` (even in dry-run); purges each expired row — `Status=deleted`, CODE row released, its `HOVTPSOURCE` rows and every blob under `<guid>/` deleted, then the row is **replaced** by a tombstone (name, code, dates, venue, created/deleted/purged times, `ExtendedCount`; no e-mail; `PurgedUtc` set); any failed step leaves no tombstone and retries next night; re-sweeps `<guid>/` for 2 days after a purge; deletes `HOVTPSESSION` rows idle > 30 d; reconciles every `COMPETITION` row into the clock table (writes only rows that differ). Purging is on by default in both environments; `RETENTION_PURGE_ENABLED=false` (Bicep param `retentionPurgeEnabled`, GitHub var `RETENTION_PURGE_ENABLED`) is the kill switch — dry-run "would purge" logs only. The HOVTP listener 451s a competition that is deleted or past its `DeletionDate`. **Clock table and the tool contract**: the tools never read `competitions`. The platform mirrors each competition into its own table `retentionclock` — PK `COMPETITION`, RK `<guid lowercase>`, columns **only** `DeletionDate`, `Status`, `PurgedUtc` (`_sync_clock`, replace mode) — on create, extend, DELETE, backfill, mark-deleted and tombstone, and the sweep reconciles it nightly. Tools read it through their shared `platform_clock.py` (table overridable with their `PLATFORM_CLOCK_TABLE`; ours is `RETENTION_CLOCK_TABLE`) and delete a linked record only on the platform's verdict, `Status == "deleted"` or `PurgedUtc` (their timers run at 04:00 UTC, after our 03:00 sweep) — keep those names. Their `resolve_competition` answers **410 `platform_deleted`** for a deleted/purged platform competition (judgepapers: plain-text body starting `platform_deleted`; protocolgenerator: JSON `{"error":"platform_deleted"}`); the tool frontends then clear the active competition and show "… has been deleted" on the pick card. Score Modifier **requires** `platformId` on `generate`/`generate_results` (400 `platform_id_required`), so its frontend only shows the tool with a competition selected. Every Extend button — the home panel's "Data is deleted automatically on … · Extend by a week" (warning in the last 7 days or when the date falls on/before the competition) and the Judge Paper Creator / Protocol Generator header (`renderRetention`) — calls only shared-ui `extendCompetition` + `setActiveCompetition`; the headers show the platform date from the active competition. App Insights keeps its default retention.

The **active competition** is client-side state (localStorage, same origin). Tools no longer keep a competition list of their own: each resolves the active competition into its own record through its `POST /resolve_competition` (`{platformId, name}` → the tool's record, created or adopted on first use), so the platform GUID is the binding key. The Protocol Generator's detail header carries a **pencil** that opens the shared edit dialog (`openEditCompetitionDialog`) and writes the result back with `setActiveCompetition`; both tool apps re-resolve whenever the active competition's *label* changes on the same GUID (a rename in another tab arrives as a `storage` event), which is what lets the tool backends sync their own record names.

## Access model (private competitions with sharing)

Each competition is visible only to its **owner** and the users it is shared with (**read** = view/download, **write** = everything else except delete and sharing); only the owner or an admin manages shares; only an admin moves ownership. The platform owns an internal **userId** (GUID) decoupled from the identity provider; grants reference only userIds. Tables (env `USERS_TABLE`, `USER_IDENTITIES_TABLE`, `COMPETITION_ACCESS_TABLE`):

- `users` — PK `USER`, RK `<userId>`: `Email` (lowercase), `DisplayName`, `FirstSeenUtc`, `LastSeenUtc`, and once the router forwards `x-forwarded-user-terms-accepted: 1` `TermsVersion`, `PrivacyVersion`, `TermsAcceptedUtc` (written on create or first sight, never overwritten, never required; `terms_outdated(accepted, current)` is the check for a future re-acceptance step). PII, platform only.
- `useridentities` — PK `IDENTITY`, RK `<tid>_<oid>` (lowercase): `UserId`, `Tid`, `Oid`, `Provider` `entra`, `CreatedUtc`. No PII; tools read it.
- `competitionaccess` — PK `<competition guid lowercase>`, RK `<userId>`: `Role` `owner|write|read`, `GrantedBy` (userId), `GrantedUtc`. Exactly one `owner` row per competition. No PII; tools read it.

`_resolve_user`: point-read the identity row; if missing, create the `users` row, then **insert** the identity row (409 → drop ours, re-read: concurrent first requests converge); `LastSeenUtc`/`Email`/`DisplayName` refreshed at most hourly per process. At user creation only, the **legacy claim** makes the new user owner of every `COMPETITION` row created before `LEGACY_CLAIM_CUTOFF` (`"2026-10-19T09:30:00Z"`, the access-model rollout — must stay ≤ the prod rollout) whose `CreatedBy` (ASCII-normalised) is their e-mail and which has **never had an owner** (the only place an e-mail grants anything; unclaimed rows are admin-only until an admin assigns an owner; audited `access.claim`); a claimed row gets `LegacyClaimedUtc` and is never claimed again, even after its owner is removed. **One owner, always:** the ownership sentinel row (`competitionaccess` RK `_owner`, `OwnerUserId`; not a GUID so never a grant, ignored by the tools) is written in the **same partition transaction** as the owner rows by create and legacy claim (insert — fails once any owner was ever set) and by the admin owner swap (insert, or etag-conditional replace; plus upsert of the new owner and an etag-conditional demotion of **every** existing owner row), so concurrent claim/swap/swap can never both land; the loser retries (swap) or backs off (claim). `CreatedBy` stays as "Created by" history. `_access_role`: admin → `owner`, else the `competitionaccess` point read (the admin's own row is read too, `_Role.own`): a user-route write that only the admin role allowed (own grant missing or too low — PUT/PATCH, DELETE, extend, file upload/delete, HOVTP accept/reject/revoke, access grant/change/revoke) writes an extra AUDIT row `admin.override.<competition.update|competition.delete|competition.extend|file.upload|file.delete|hovtp.accept|hovtp.reject|hovtp.revoke|access.grant|access.change|access.revoke>` after it succeeded. `_require_access(user, id, need)`: none → **404 `not_found`** (decided before any write, same as a missing id), read on a write route → **403 `read_only`**, short of owner on an owner route → **403 `owner_required`**. Matrix — read: GET competition, list/download files, list HOVTP sources; write: PUT/PATCH, extend, upload/delete file, HOVTP accept/reject/revoke; owner: DELETE, the access routes. `GET /api/competitions` = the caller's grant rows (`RowKey eq '<userId>'`) → point reads — admins too (their view of everything is `/api/manage`); every competition response carries `access` (caller's effective role) and `owner` (`{userId,name,email}` or null). Create writes CODE → COMPETITION → owner row, undoing the earlier rows if a later one fails. Share routes: `GET …/access` (owner) → `{"items":[{userId,name,email,role}]}` owner first; `PUT …/access/{userId}` `{"role":"read"|"write"}` (owner; target must be in `users`, never the owner row or yourself: `invalid_role`, `invalid_user`, `user_not_found` 404, `cannot_target_self`, `cannot_change_owner`, `competition_deleted` 409) → `{"item": Grant}`; `DELETE …/access/{userId}` (owner, or the grantee itself = leave; `{userId}` may be `me`; `grant_not_found` 404) → `{"status":"removed","userId","left"}`. `GET /api/users/search?q=` → `{"items":[{userId,name,email: string|null,emailHint}]}` (≤ 8, never yourself): q a complete e-mail (printable ASCII, one `@`, no spaces) → exact case-insensitive match, full `email`; otherwise ≥ 3 chars (else 400 `query_too_short`) → substring of `DisplayName` **only**, `email: null` + `emailHint` (`a•••@club.fi`) except for people the caller already shares any competition with (either direction, any role), who get the full e-mail. Rate limit shared across instances in the `users` table (PK `SEARCHRATE`/RK userId: `MinuteStart/Count`, `DayStart/Count`, etag-conditional increments): 30/min and 300/day per user → 429 `rate_limited`; unreadable counter → 500 (fail closed); search scans only PK `USER`. `GET /api/users/recent` (grantees of competitions you own) → `{"items":[{userId,name,email}]}`; `GET /api/users/me` → `{userId,name,email,isAdmin}`. Grant/change/revoke/leave/owner change are `adminlog` AUDIT rows for every user (`Actor`, `Target` e-mail, `{"role":[before,after]}`). Retention: soft delete keeps grants (restore keeps its shares); `_purge_competition` deletes the partition's access rows before the tombstone (re-sweep too); nightly step 7 removes users unseen > `INACTIVE_USER_DAYS` (365) who own no live competition — re-reads the users row first (skipped if seen since), then grants, identity rows, the users row (etag-conditional on that re-read) and its `SEARCHRATE` row — under the purge kill switch.

**Tool contract** (`platform_access.py`, byte-identical in fs-judgepapers, fs-protocolgenerator, fs-scoremodifier): `role_for(platform_id, tid, oid, is_admin)` → `useridentities` then `competitionaccess` lookup, 30 s in-process cache; settings `PLATFORM_IDENTITIES_TABLE`, `PLATFORM_ACCESS_TABLE` (+ the existing `PLATFORM_STORAGE_ACCOUNT`); `is_admin` = the router's `x-forwarded-user-admin: 1`. Errors: no access / unknown / legacy record without `PlatformId` for a non-admin → 404 `platform_not_found`; read caller on a write route → 403 `platform_read_only`; tables unreadable → 503 `platform_unavailable`. Keep these table, column, header and error names stable.

**Frontend.** shared-ui `PlatformCompetition` carries `access` and `owner` (validated, mapped and serialized into the stored selection, so `refreshActiveCompetition` propagates a role change to every tab; a missing `access` reads as `owner` — `competitionAccess`/`isReadOnlyCompetition`/`canManageCompetition`). Clients `listAccess`, `setAccess`, `removeAccess`/`leaveCompetition` (`me`), `searchUsers` (→ `UserSearchHit[]`; show `searchHitEmail(hit)` = `email ?? emailHint`; no request under `USER_SEARCH_MIN_CHARS`), `recentShareUsers`, `getMe`; `CompetitionApiError.code` holds the API's machine code. `platform_read_only` (403) is a `PlatformErrorCode` but **not** "gone" — the selection stays. `share-dialog.ts` `openShareCompetitionDialog(comp)` (the competition dialog's pattern: grants list with read/write select + Remove, owner row fixed, a 250 ms / ≥ 3-char ARIA combobox type-ahead with arrow keys + Enter, "Recent" quick picks); the nav selector badges "Shared" / "View only". ## Admin panel

`/admin/` (`site/src/admin/`: `main.ts` path-based tabs `/admin/`, `/admin/competitions/<id>`, `/admin/users`, `/admin/diagnostics`, `/admin/audit`; `api.ts` client). The code is public on purpose — the gates are the security, not obscurity. **Admin = the app role `Site.Admin`** (`ADMIN_ROLE`, default `Site.Admin`, optional GitHub var override; assigned to a group in each tenant — `infra/EXTERNAL-ID.md`), in both tenant modes; it implies the External ID access role. There is **no** e-mail list and no break-glass e-mail. Enforced twice:

- **Router** (`isAdminRequest` in `server.js`: the role in the principal's `roles` claim or `…/claims/role`; needs the full identity — a decodable `X-MS-CLIENT-PRINCIPAL` with oid + tid from an allowed tenant — or `DEV_FAKE_USER` + `DEV_FAKE_ROLES=Site.Admin`, both blanked by `NODE_ENV=production`, set by `webapp.bicep`). Also sets `x-forwarded-user-admin: 1`. Drives `isAdmin` in `/userinfo` (the user menu's "Admin panel" link in `setupUserMenu`). `/admin/*` documents are a plain 404 for non-admins (`DOCUMENT_PREFIXES` gives the SPA fallback; `admin` is not in `TOOLS`). `/api/manage/*` is 403 `admin_required` without proxying; non-GET needs same-origin like every proxied API (see Router request hygiene). Gates match the canonical, case-insensitive path. `GET /admin/api/diagnostics` is router-native: build info (`build-info.json` next to `server.js`, written by deploy-frontend), configured targets/secrets as **booleans only**, and parallel 10 s `/api/health` pings (`HOVTP_HEALTH_URL` for the listener; every backend has an ungated `/api/health` — a 404 shows as `no_health_route`).
- **Platform** `_require_admin` (`function_app.py`): **fails closed** — `PROXY_SHARED_SECRET` must be set and match (`hmac.compare_digest`), forwarded tid/oid present and tid allowed, then `X-Forwarded-User-Admin: 1` from the router (the same trust the tools place in it; `User.is_admin` for the user routes' admin override comes from the same header); reads no table. The audit actor is the forwarded e-mail, or `<tid>_<oid>` without one. Routes `manage/...` (the Functions host reserves `admin`): list all incl. tombstones (`?status=active|deleted|purged|all`, each with `owner`), detail (clock row, file + HOVTP counts, `access` list), PATCH (shares `_apply_competition_edit` with the user PATCH; adds `deletionDate` ≥ tomorrow 00:00 UTC, synced to the clock table at once; `createdBy` is read-only history → 400 `created_by_read_only`), `PUT …/{id}/owner` `{"userId"}` (one `submit_transaction` in the competition's partition: ownership sentinel inserted/etag-replaced, new owner row upserted, every old owner row → `write`, etag-conditional with retries; works on unowned legacy rows; `user_not_found` 404, `purged` 409) → `{"competition","access"}`, `GET manage/users[?q=]` → `{"users":[{userId,name,email,firstSeenUtc,lastSeenUtc,owned,shared,identities}]}` (`q`: name/e-mail substring, ≥ 3 chars, ≤ 8), `restore` (soft-deleted only; re-claims the CODE row, 409 `code_in_use`/`purged`/`purging`; never rolls back a claim a concurrent restore may have adopted), `purge` (`{"confirm": code}`; `_soft_delete` + `_purge_competition` → tombstone; ignores `RETENTION_PURGE_ENABLED`). `_purge_competition` (sweep and admin) first claims the row with one conditional write (`Status=deleted` + `PurgingUtc`), even when already deleted, so a restore either wins that race or refuses afterwards, DELETE, `sweep/dry-run`, `diagnostics`, `audit`.
- **Audit**: table `adminlog` (`ADMIN_LOG_TABLE`; platform MI only). `PK=AUDIT` rows (RK inverted ticks + uuid: actor e-mail, action, competition id/code, `Target` e-mail for access changes, changed fields `{field: [before, after]}`, outcome), best-effort after success — admin mutations plus every user's `access.*` and `competition.owner`; `PK=SWEEP` rows record every sweep run (nightly + manual dry-run). The nightly sweep prunes AUDIT > 365 d and SWEEP > 30 d — obeying the purge kill switch. The privacy notice states the admin role and the 1-year log.

Phase 2 (admin from the `Site.Admin` app role instead of `ADMIN_EMAILS`) is implemented. Phase 3 (private competitions with sharing) is implemented — see Access model.

## Changelog ("What's New" panel)

Commits are served by the **router**, not the browser: `GET /changelog-live?branch=main|test` (both serve the `main` feed; `server/server.js`) reads `site/public/changelog-sources.json` (incl. `fs-protocolgenerator`), fetches `/repos/<repo>/commits?sha=<branch>&per_page=20` per repo, drops commits whose message contains `#nowhatsnew` or `#nowhatnew` (anywhere, any case — `CHANGELOG_HIDE_TAG`; the frontend's direct-GitHub fallback and `scripts/generate-changelog.sh` apply the same filter), maps/merges/sorts to the frontend entry shape, and caches per branch **in memory for 10 min** with in-flight dedup — the whole site costs GitHub four calls per 10 min instead of four per page load against the 60 req/hr-per-IP anonymous limit. All-or-nothing per refresh (one bad repo fails it, never a partial cache); on failure a previous result is served **stale**, and with nothing cached it's a 502. Invalid branch → 400.

Frontend chain (`site/src/main.ts` `loadChangelog`): `localStorage` cache (5 min, key `changelog-cache-v1`) → `/changelog-live` → direct GitHub API (`fetchLiveChangelog`, kept so `vite dev` works without the router) → build-time `/changelog.json` from `scripts/generate-changelog.sh` → "Changelog not available.". Always the `main` feed, in every environment (`changelogBranch()` returns `main`; the router still accepts `?branch=test` from older cached frontends but serves it from the `main` cache entry, and the deploy generates the fallback from `main`) — the repos have no long-lived `test` branch. Tool repos must stay public. New tool in the feed = one JSON entry + a `.changelog-badge--<tool-slug>` CSS rule.

## Commit messages

Surfaced **verbatim** in the public "What's New" panel: one plain user-facing title line (sentence case, no `type(scope):`), blank line, then `-` bullets per notable change. Keep bullets tight (~150 chars collapse threshold); trailers render too, so keep bodies to the bullet summary. A commit that users shouldn't see (dependency bumps, CI, docs) carries `#nowhatsnew` anywhere in its message and is left out of the panel.

## Deployment

**Flow (no long-lived `test` branch):** branch from `main` → dispatch `deploy-site.yml` on that branch with `environment=test` → PR to `main` → merge → push to `main` deploys prod → the branch is auto-deleted on merge. `main` is guarded by a ruleset: PR required, code-owner review (`.github/CODEOWNERS`: `* @mmaraa`), squash only, the `pytest`, `hovtp-pytest` and `frontend` checks (`.github/workflows/ci.yml`, every PR) must pass, no force-push/deletion; repository admins can bypass, which is how the owner merges their own PRs. The `prod` GitHub environment only accepts deployments from `main`; `test` accepts any branch and holds whichever was deployed last.

`.github/workflows/deploy-site.yml` — push to `main` → prod; `test` only via `workflow_dispatch`. Five jobs: `set-environment` → `deploy-infra` (bicep + FIC/redirect-URI Graph step) → `deploy-platform-backend` (pytest, then zip deploy) → `deploy-hovtp-backend` (same shape for `infra/hovtp`, plus a warning-only `OPTIONS /api/v1/hovtp` smoke check) → `deploy-frontend` (builds + router tests, stages `server/server.js` + `site/dist/*` → `public/`, async zip deploy + Kudu poll, `/health` smoke check). Dependabot version updates (`.github/dependabot.yml`, read from `main` only) open their PRs against `main` like any feature branch: CI checks them, they wait for code-owner review, and merging one deploys prod — dispatch its branch to `test` first when the update is risky.

Per-environment GitHub config: vars `FUNCTION_APP_URL_{JUDGEPAPERS,SCOREMODIFIER,PROTOCOLGENERATOR,GDPRTOOL}`, `TOOL_PRINCIPAL_ID_{…}`, `SKIP_CUSTOM_DOMAIN` (set `true` to run on the default hostname, e.g. pre-cutover), `AUTH_LOGIN_PROVIDER` (optional; Easy Auth provider for `/signin`, default `aad`), `AUTH_TENANT_MODE` (optional; `workforce` default | `external` — test `external`, prod `workforce` until phase C) with `EXTERNAL_TENANT_ID` / `AUTH_EXTERNAL_CLIENT_ID` / `AUTH_EXTERNAL_AUTHORITY_HOST` / `EXTERNAL_ACCESS_ROLE` (Entra External ID — vars only, there is no External ID secret; see `infra/EXTERNAL-ID.md`), `ADMIN_ROLE` (optional; the admin app role, default `Site.Admin` — there is no admin e-mail list), `ALLOWED_TENANT_IDS` (optional; comma-separated Entra tenant ids for the router and the platform API; unset = the deployment tenant), `HOVTP_ENABLED` (optional; `false` = the deployed HOVTP listener answers every request 503 — defaults are on in test, off in prod), `RETENTION_PURGE_ENABLED` (optional kill switch; `false` = the platform `retention_sweep` only logs what it would purge — unset means purge, in both environments); secrets `PROXY_SHARED_SECRET_{JUDGEPAPERS,SCOREMODIFIER,PROTOCOLGENERATOR,GDPRTOOL,PLATFORM}`, `PROXY_SHARED_SECRET_HOVTP` (test only — the value APIM injects, from the `azure-publishing` repo), `AUTH_CLIENT_ID`, `AUTH_APP_OBJECT_ID`. Bicepparams read secrets via `readEnvironmentVariable()`. `deploy-infra` is **atomic**: `webapp.bicep` still replaces the whole app-settings collection, but it now writes the full set itself (`FUNCTION_APP_URL_*` — platform from the platform Function App module's output, the tools from the GitHub env config passed into the template — plus `PROXY_SHARED_SECRET_*`, `AUTH_LOGIN_PROVIDER` and `SCM_DO_BUILD_DURING_DEPLOYMENT`; the platform Function App's settings, incl. `RETENTION_PURGE_ENABLED`, come from `platform-function.bicep`), so running it alone leaves the router fully configured.

`packages/shared-ui` is a private workspace package (`"private": true`, no `publishConfig`, no `.npmrc` registry scope): the site consumes it via the workspace symlink only, and the old GitHub Packages publish (`publish-shared-ui.yml`, v2.x for the tool repos' legacy frontends) is retired with those frontends. Migration/cutover order, old-subdomain redirects and the teardown checklist live in `infra/MIGRATION.md`. All jobs in the workflows pin `runs-on: ubuntu-26.04` rather than `ubuntu-latest` ([actions/runner-images#14748](https://github.com/actions/runner-images/issues/14748) flips `-latest` from 24.04 to 26.04 between 2026-10-19 and 2026-11-19); bump that label deliberately — verify via a `test`-environment dispatch first, roll back to `ubuntu-24.04` if needed — and never set it back to `ubuntu-latest`.

## Infra notes

- Two environments; `test` provisioned on demand, torn down manually (`rg-fs-site-test`). The DNS RG (`rg-fs-dns`) is shared and persistent; deployments are incremental and only touch their own record sets (hand-seeded MX etc. survive — `infra/seed-dns-records.sh`).
- Apex binding is a literal A record to the app's `inboundIpAddress` (alias records can't target App Service); each infra run self-heals it. Managed certs support the apex (HTTP-token validation works behind Easy Auth).
- App Service has a hard ~230 s request timeout — fine for current PDF generation, but future long-running FSM batch work needs an async/polling pattern.
- Tool Function Apps are reached **only** through the router (CORS cleared, `AllowAnonymous` + proxy-secret gate). The per-tool header contract is documented in each tool repo's `PROXY-CONTRACT.md`.
